# Alice AI — Windows x64 packaging requirements INPUT (M5).
#
# This is the cross-OS dependency set for the WINDOWS frozen build. It mirrors
# backend/requirements.txt but makes the one platform-specific swap the package
# turns on (PLAN §6, the mlx→llama_cpp swap):
#
#       macOS arm64 runtime  =  mlx + mlx-lm        (Apple Metal)
#       Windows x64 runtime  =  llama-cpp-python    (GGUF: CPU default / CUDA opt)
#
# The application code is OS-agnostic — alice_acp.local_inference's
# ``runtime_for_probe`` maps the host to a ModelRuntimeFamily (Apple→mlx,
# NVIDIA→cuda, AMD/CPU→gguf/cpu) and the adapters import mlx_lm / llama_cpp
# LAZILY in the matching branch only. So on Windows mlx is simply never imported;
# we just don't install it here, and we DO install llama-cpp-python.
#
# ---------------------------------------------------------------------------
# HASH-PINNED LOCK: generate ON WINDOWS, never hand-edited.
# ---------------------------------------------------------------------------
# Wheel hashes are per-platform — a lock generated on macOS cannot install on
# Windows (different .whl artifacts). The Windows CI job (release.yml) and
# build_exe.ps1 compile this file into backend/requirements.lock.win.txt with:
#
#   pip install uv
#   uv pip compile --generate-hashes --no-header `
#       backend/requirements.win.txt -o backend/requirements.lock.win.txt
#   pip install --require-hashes -r backend/requirements.lock.win.txt
#
# Commit the generated requirements.lock.win.txt (produced by CI on windows-2022)
# so the release build is reproducible + hash-enforced, exactly like the macOS
# requirements.lock.txt. Until that first Windows CI run lands it, this input
# file is the source of truth and the build compiles the lock on the fly.
# ---------------------------------------------------------------------------
